Weight-Space Programming Manual

This manual describes the project in weight-space-programming. The project tests one claim: an LLM can read and write neural network weights without training. The text follows the spirit of ASD-STE100 [18]. Document date: 6 November 2026.

Summary of results

  • Read test. Claude named Breakout from the raw weights, with confidence 93%. The sample is one network.
  • Read control. The rows of W1 were shuffled. Claude found the shuffle, reduced its confidence to 60%, and named Breakout again. The control did not remove all the information.
  • Write test. Claude wrote a Breakout network in one reply. The network scored 269.4 ± 7.4. The published scores are 25.3 for PPO at 500M steps and 517.4 for GPT-6 Astra.
  • Three Pads. Claude wrote three networks in three separate replies. Each network landed in 3,000 of 3,000 flights, with a fixed pad and with a pad change.
  • Limit. Three Pads is an easy control task for Claude. No network reads the fuel input. All three networks failed when the start fuel was low.
  • Tank detection. The method did not give a useful detector on a real image task. Plain fixes, training and a ready-made detector are better. Section 12 gives the full account. The author's note: this experiment did not go as I would like, but that is okay. Not everything has to be a success. We learn from our failures.

2.2 The second report

Chandan Singh published a report [3] and code [4] on the same topic. Claude operated as a coding agent with code execution. Three findings affect this project:

  • Claude wrote 959 programs for 13 tasks. All ten algorithmic tasks reached 100% within three attempts.
  • On language tasks, the agent could read the data for evaluation. The agent then fitted that data. This made the SNLI [14] score invalid. This project prevents that fault with the isolation in section 4.
  • In a test with a baseline, reading Qwen weights improved edit predictions by a correlation of only +0.06 ± 0.02. This project therefore includes a control.

2.3 The Medium article

The article by Mehmet Özel [5] is for paying members. The visible part repeats the Experiment 8 numbers of the main post. That part adds no new data. This project did not use it. The remaining text was not read.

4. Isolation of the LLM

An LLM with access to answers or evaluation data can give a false result. The tool calls Claude Code [19] and makes each call as follows:

  • The call runs in a new, empty, temporary folder. The folder contains no answers.
  • --tools "" removes all tools.
  • --strict-mcp-config removes all MCP servers.
  • --setting-sources "" removes user and project settings, including hooks.
  • CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 and CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 remove instruction files and memory.
  • --system-prompt sets one neutral sentence: "Answer the user's request."

After each call, the tool reads the raw event stream. The run is usable only if the stream shows no offered tools, no MCP servers and no tool calls. The score command stops if the run fails this audit. All six live runs in sections 5 to 8 passed the audit. Section 12.8 describes the Codex path.

The tool saves a filtered copy of the event stream. The filter keeps only listed fields: model, tools, reply text, reasoning text, token counts and outcome. It removes machine paths, session and request IDs, account limits and reasoning signatures. The audit of a filtered copy gives the same result as the audit of the full stream.

NOTE A probe with a separate question showed what remains in the context. Claude Code adds a short environment block, the date and the account email address. None of these describe games or weights. The probe found no CLAUDE.md, memory or plugin text.

5. Experiment 1: read weights

5.1 Method

The tool sends the authors' exact prompt for their Breakout network. The prompt holds 17,253 weights as text, to 3 decimal places. The prompt does not name the game. The tool uses the same reasoning effort as the authors: high.

The control uses the same prompt, with the 500 rows of W1 in random order. Each row keeps its values. The prompt still says that row i belongs to input i. That statement is now false.

5.2 Results

TestGame line in the replyConfidence

W1 rows shuffledBreakout (a brick-breaking paddle game, also similar to Arkanoid)60%

The control result was not the expected result. The expected result was a false, confident answer. In the actual reply, Claude wrote that the rows "look scrambled by a fixed permutation". Claude then counted the row types and used those counts as evidence.

5.3 Interpretation

  • The counts are near the measured values. The reply is therefore not a made-up story.
  • Shuffling rows does not remove the row values or the output layer. A stronger control must remove those too.
  • Breakout is a well-known game, so its prior chance is high. This project did not measure that prior chance.
  • One network and one control are a small sample.

6. Experiment 5: write weights

6.1 Offline proof of the scorer

A wrong parser or scorer gives wrong conclusions. The verify command therefore tests the tool on the authors' data, with no LLM call. It does these checks:

  • It reads the 7 saved replies of Experiments 1 and 2. All guesses and all confidence values agree with the authors' scores.
  • It parses the 3 saved replies of Experiment 5. All weights are exactly equal to the authors' hand.npz files.
  • It plays each saved network for 1,000 episodes, on MinAtar [7] version 1.0.15 [8].

6.2 Live result

Claude received the authors' exact Breakout prompt, with reasoning effort xhigh. The tool read 95 of 95 statements. The network has 757 nonzero weights of 20,486. Its mean is 269.4 ± 7.4 over 1,000 episodes, and its highest score is 834.

Claude's network scored more than ten times the published PPO values, and about half of Astra's score. PPO is a low baseline here, because the network is a small MLP. This project did not test a plain program on Breakout.

7. Three Pads: the game

Three Pads is an original landing game for this project. It uses no art, no levels and no name from an existing game. A craft falls under gravity. Three pads are on flat ground. The pilot must land slowly on the target pad.

7.1 Rules

Each tick, the pilot selects one action. There are four actions: none, thrust, left and right. There is a 10% chance that the game repeats the previous action. This is the same "sticky action" rule as in MinAtar.

The complete source of the rules is below. The LLM received this exact text.

// Three Pads: the complete game rules. The browser, the scorer and the prompt all use this file.
(function (root) {
  const WIDTH = 100, HEIGHT = 60, CEILING = 80;
  const PADS = [20, 50, 80], PAD_HALF_WIDTH = 4;
  const GRAVITY = 0.01, MAIN_THRUST = 0.025, SIDE_THRUST = 0.008;
  const FUEL = 300, MAIN_BURN = 1, SIDE_BURN = 0.5;
  const SAFE_VX = 0.1, SAFE_VY = 0.25;
  const MAX_TICKS = 1000, STICKY = 0.1;
  const ACTIONS = ['none', 'thrust', 'left', 'right'];

  function reset(rng, target) {
    return {
      x: 10 + 80 * rng(),
      y: 50 + 8 * rng(),
      vx: -0.2 + 0.4 * rng(),
      vy: -0.1 * rng(),
      fuel: FUEL,
      target,
      tick: 0,
      lastAction: 0,
      outcome: null,
    };
  }

  // The network's input: 8 numbers.
  function observe(s) {
    return [s.x / WIDTH, s.y / HEIGHT, s.vx, s.vy, s.fuel / FUEL,
      s.target === 0 ? 1 : 0, s.target === 1 ? 1 : 0, s.target === 2 ? 1 : 0];
  }

  // Advances one tick. An engine fires only if fuel is left. Exactly one action happens per tick.
  function step(s, action, rng) {
    if (s.outcome) return s;
    if (rng() < STICKY) action = s.lastAction;
    s.lastAction = action;
    let ax = 0, ay = -GRAVITY;
    if (action === 1 && s.fuel >= MAIN_BURN) { ay += MAIN_THRUST; s.fuel -= MAIN_BURN; }
    if (action === 2 && s.fuel >= SIDE_BURN) { ax -= SIDE_THRUST; s.fuel -= SIDE_BURN; }
    if (action === 3 && s.fuel >= SIDE_BURN) { ax += SIDE_THRUST; s.fuel -= SIDE_BURN; }
    s.vx += ax;
    s.vy += ay;
    s.x += s.vx;
    s.y += s.vy;
    s.tick += 1;
    if (s.y <= 0) {
      s.y = 0;
      const pad = PADS.findIndex((p) => Math.abs(s.x - p) <= PAD_HALF_WIDTH);
      const soft = Math.abs(s.vx) <= SAFE_VX && Math.abs(s.vy) <= SAFE_VY;
      if (pad < 0) s.outcome = 'off_pad';
      else if (!soft) s.outcome = 'crashed';
      else s.outcome = pad === s.target ? 'landed' : 'wrong_pad';
    } else if (s.x < 0 || s.x > WIDTH || s.y > CEILING) {
      s.outcome = 'lost';
    } else if (s.tick >= MAX_TICKS) {
      s.outcome = 'timeout';
    }
    return s;
  }

  const api = { WIDTH, HEIGHT, CEILING, PADS, PAD_HALF_WIDTH, GRAVITY, MAIN_THRUST, SIDE_THRUST,
    FUEL, MAIN_BURN, SIDE_BURN, SAFE_VX, SAFE_VY, MAX_TICKS, STICKY, ACTIONS, reset, observe, step };
  if (typeof module !== 'undefined') module.exports = api;
  else root.Sim = api;
})(globalThis);

7.2 State

The pilot sees 8 numbers. Inputs 5, 6 and 7 tell which pad is the target pad. The target pad can change during a flight. The network must then change its course.

7.3 Network

The network is an MLP with 8 inputs, two hidden layers of 16 units, and 4 outputs. It has 484 weights. The activation function is tanh. The action is sampled from the softmax of the outputs.

h1     = tanh(x  @ W1 + b1)    W1: 8 x 16    b1: 16
h2     = tanh(h1 @ W2 + b2)    W2: 16 x 16   b2: 16
logits =      h2 @ W3 + b3     W3: 16 x 4    b3: 4

7.4 Prompt

The prompt follows the authors' Experiment 5 prompt. It has the task, the rules source, the input layout, the network, the score method and the format of the edits block. All weights start at 0. The LLM sets only the weights that it needs. It gets no feedback.

W1[2, 0] = 2.5                     # one entry
W1[0:6, 3] = [1, 0, -1, 0, 2, 0]   # values along a range
b1[0:4] = -1                       # fill a range
W3[:, 2] *= 2                      # scale (also += and -=)
WARNING The reply is untrusted text. The parser reads numbers with ast.literal_eval. It does not run the reply as code. A test confirms that a reply with code cannot run that code.

7.5 Score method

  • Fixed pad test. 3,000 flights. Each pad is the target pad in one third of the flights.
  • Pad change test. 3,000 flights. The target pad changes once, at a tick from 30 to 120.
  • Seeds. The seeds start at 1,000,000. The LLM does not see them.
  • Baselines. The random pilot shows the lower limit. The plain program shows what simple code can do. The plain program was written once and was not tuned.

7.6 The page

The page is one HTML file with two small scripts. It needs no server. A person can fly the craft or select a network. The page shows the 8 inputs, the chance of each action and all the weights in real time.

The three replies use the same design. Each reply calculates a desired speed for each axis. It then fires the engine that reduces the speed error. Each network holds its height until the craft is over the target pad. This prevents a touchdown outside the pad. The holding height differs: the replies state about 8, 12 and 20.

The networks use few weights. W1 has one row for each input, and row 4 is the fuel input. In all three networks, row 4 is all zeros. No network uses the fuel value.

9. What the results show

9.1 The results support these statements

  • Claude Opus 5.5 can write working network weights from source code, with no tools, no feedback and no training. This occurred in 4 of 4 write replies on the two games.
  • The written networks work on seeds that Claude did not see.
  • On a small network, Claude can read real structure from the numbers. Its counts in section 5.2 agree with measured values.
  • The Three Pads result is repeatable: three of three replies landed in all flights.

9.2 The results do not support these statements

  • They do not show that Claude can write networks for hard tasks. Three Pads has a direct 8-number state and a known control method. Section 12 shows a harder task, where the written networks do not beat plain fits.
  • They do not show that this method is better than a program. The networks contain a control program in weight form. The plain program lands more often at fuel 100 and 60.
  • They do not show that Claude can read large models. The largest network that an LLM read in this project has 20,486 weights.
  • They do not measure Claude against Astra in general. The comparison is one reply on one game.
  • They do not give a full view of the read skill. The project ran one network and one control.

10. Procedures

Do all procedures in the project folder. The requirements are uv [20], Node, and a Claude login for LLM calls. The browser test uses Playwright [21], which uv sync installs at a fixed version. The project was tested on Node 26 and Python 3.13.

10.1 Install the project

  1. Run uv sync.
  2. Run .venv/bin/python wsp.py fetch.
  3. Run .venv/bin/playwright install chromium. Only the browser test and the screenshots need this.

10.2 Fly the craft

  1. Open lander/index.html in a browser.
  2. Set the pilot to You.
  3. Press 1, 2 or 3 to select the target pad.
  4. Press the up arrow to fire the main engine.
  5. Press the left arrow or the right arrow to move the craft.
  6. Reduce speed until the page shows Touchdown speed: safe.
  7. Touch down on the green pad.
  8. Press R to start a new flight.

10.3 Watch a network

  1. Set the pilot to Claude reply A.
  2. Watch the flight.
  3. Press 3 during the flight to change the target pad.
  4. Watch the craft change its course.
NOTE An engine control changes the pilot to You. To return to the network, set the pilot again.

10.4 Run all tests

  1. Run node --test lander/test.js.
  2. Run .venv/bin/python -m unittest discover -s tests.
  3. Run .venv/bin/python tests/e2e_lander.py.
  4. Run .venv/bin/python wsp.py verify.
  5. Read the output. Each line must start with ok.

The verify command needs no LLM. A full run writes results/verify.json, and the manual reads that file. A run with fewer episodes does not change that file.

12. Tank detection experiment

AUTHOR'S NOTE This experiment did not go as I would like, but that is okay. Not everything has to be a success. We learn from our failures. This section therefore keeps the failures in full.

12.1 Purpose

Sections 5 to 8 use games. A game has source code, so the LLM can read the exact rules. This experiment applies the method to a different type of task: find circular storage tanks in an overhead image. An image task has no source code. The LLM can get only measured numbers.

The experiment asks three questions:

  1. Can an LLM repair a trained detection network with weight edits and no training?
  2. Can an LLM write a working detection network from zeros?
  3. How do these results compare with plain fixes, real training and a ready-made detector?

12.2 Result in brief

  • Repair. The repair is better than no edit. It shows no practical gain over plain fixes. The rule set before the replies reads "no skill", because the control did not collapse.
  • Write. Claude and GPT-6 Astra each wrote working detectors from zeros. The rule set before the replies reads "some design skill, no practical gain" for both.
  • Detector. Zero-shot RT-DETRv2 [28] is the best choice to find and count tanks on this image. It found 23 of 28 test tanks, with 2 false objects.
  • Outlines. A ResNet18 U-Net trained on the new image is the best choice for exact outlines.
CAUTION The sample is small: one image pair, 19 val tanks and 28 test tanks, and 3 replies for each LLM test. Do not use small differences between rows as real differences.

12.3 Data

The data are two private overhead RGB images of one industrial area, from different dates. This project does not publish the images, the masks, the tank positions or the place. Figures in this section therefore use charts and a synthetic scene.

ItemValue

Pixel gridBoth images are warped to one grid of 4,749 x 3,221 pixels, at the pixel size of the 2015 image, about 0.8 m. Thus scale is not part of the fault.

CellsThe area is divided into cells of 250 m. Each cell goes to one partition: 153 train, 30 val, 38 test. The partitions hold 50, 19 and 28 tanks.

Partition rules:

  • Train pixels are the only pixels that a fit or a prompt can read. The tool replaces all other pixels with the band mean before each fit. Without this step, a tile or a blur can carry a hidden pixel into a train value.
  • Val cells select between methods.
  • Test cells report results. They selected no network and no reply.
  • In the 2015 image, the places of the val and test cells are hidden too. One sixth of the train cells selects the epoch of the source network.

12.4 Metrics

MetricDefinition
Pixel IoUTank pixels found, divided by the union of the found and the true tank pixels, in one partition.

12.5 The network and the fault

The network is a U-Net [24] with a ResNet18 encoder [25], from Segmentation Models PyTorch [30]. It has 14,328,209 weights. One reply can write only some thousands of numbers. Thus a reply can edit a small part only, or leave most weights at 0.

Training settings for all ResNet18 U-Nets:

SettingValue
Start weightsImageNet encoder.
InputCrops of 256 x 256 around random train pixels, batch of 32, flips and quarter turns.
LossBinary cross-entropy plus Dice, on train pixels only.
OptimizerAdamW, learning rate 5e-4, weight decay 1e-4, one-cycle schedule.
Length40 epochs of 25 steps. The best epoch on the selection pixels is kept.
HardwareOne RTX PRO 6000 card for each run. Three seeds of the source network, plus one with colour jitter.

The source networks reach 0.71 to 0.74 IoU on hidden 2015 cells. On the new image, seed 0 falls to 0.386 val IoU. A network trained on the new image reaches 0.837. The rule set before the result was to stop if no edit reaches 90% of that value. No edit reaches 46%. Thus the fault is real, and seed 0 is the repair target. That choice was fixed before any result.

12.7 Stage B: repair by an LLM

The prompt gives the task, the network, the current head weights and a table of measured numbers. The numbers come from train cells only. The table holds:

  • the mean and the spread of each of the 16 head input channels, for tank interior, tank edge and background;
  • the within-class covariance of those channels;
  • the BatchNorm shift of each layer between the two images;
  • the source and the new statistics of encoder.bn1 and of the last decoder BatchNorm, channel by channel;
  • the current scores on the train cells.

The control is the same prompt with the channel rows shuffled in the tables. The head weights stay true. The prompt does not say that the rows are shuffled.

BatchNorm divides each channel by a stored spread, after it removes a stored mean: y = (x - running_mean) / sqrt(running_var + eps). In encoder.bn1, the mean shift is 1.23 stored standard deviations. All later layers are at 0.19 or less. The median ratio of new variance to stored variance is 7.82 on the 56 live channels. The other 8 channels are near zero in both images.

All 6 replies passed the tool audit. The columns of the table below mean the following. For a repair or a control, "Weights" is the count of changed weights. For a write reply, it is the count of weights that are not zero. Seconds is the time of one call. The Codex path reports no cost figure. Claude used 7.49 USD for 9 replies, by the figure of the CLI. See the caution about this figure in section 4.1.

  • The mean alone makes the network worse, at 0.101 IoU.
  • A shuffle that writes a near-zero variance on a live channel fails each time, because the division makes that channel very large. This explains control 41914.
  • Thus row order has a small effect, and this control cannot separate a reader from a copier.

What the test does not show

  • The prompt gave away the answer. The table lists the new encoder.bn1 values. A program that selects the layer with the largest shift makes the same network.
  • The 3 repairs are one result, because they have the same effect.
  • "No skill" means that this test did not show skill. It does not show that the LLM has no skill.

An observation outside the gate

All 3 control replies found the shuffle, with no prompt to look for it. Each one multiplied kernel sums by channel means. Each one found that the result did not match the measured logit: about -12.8 against +1.29 on tank interior. Each one then left the head alone. No repair reply reported a shuffle. This is 3 of 3 against 0 of 3. It was not a planned test. It suggests that the replies read the table against the weights.

12.8 Stage C: write from zeros

Gate 1 skipped this stage. The owner asked for it after that result, so it ran under its own rule. The rule was set before any reply:

Median of 3 replies, val IoUMeaning
At or below the fact ruleNo skill past the fact sheet.
Above the fact rule, at or below filter LDASome design skill, no practical gain.
Above filter LDAA strong result. It is not expected.

The network is geo/tiny.py, a U-Net of 5 levels with ReLU, average pooling and 16,961 weights. That size is near the Breakout network. The prompt holds its source. A test measures its receptive field. The first design measured 158 pixels, below the 164 pixels of the largest tank. One more bottleneck layer fixed this before any prompt was sent.

All weights start at 0. The prompt holds the source and a fact sheet from the train cells: band mean and spread for each pixel class, local texture, tank share and tank diameters. It has no pixels and no answer table. The fact rule is a plain program that uses the same numbers: gray above the midpoint of two class means. It reaches the network through the edits parser, in 7 weights.

Results

The median Claude reply scores 0.505 val IoU. The median Astra reply scores 0.460. Both are above the fact rule (0.131) and below filter LDA (0.523). The rule reads "some design skill, no practical gain" for both. The difference from filter LDA is small for Claude, so this is a near tie and not a clear loss. Zero and random networks score 0.000 to 0.028 val IoU.

These plain rules use only the fact sheet. They came after the replies, because the fact rule was a weak bar. They do not change the verdict. All 3 Claude replies beat them. Two of the 3 Astra replies beat them.

The designs

The replies use different designs. All of them find pale regions at more than one scale.

  • Claude 54464. It uses a logit of about F + 1.5 G + G8 - 1.5. F is a paleness value at full resolution. G and G8 are averages of F at two coarser scales, which fill dark patches inside large tanks. It uses 140 weights.
  • Claude 54468. It uses a logit of 1.3 P + S + 2 F - 1.35. It also adds a suppressor for long thin objects. It uses 305 weights.
  • Astra replies. These test for shape. They compare the centre with samples in four opposing directions, at radii such as 8, 16, 32, 48 and 72 pixels. They use 345 to 525 weights.

Claude and Astra

  • Astra found 15 to 17 of 28 test tanks, and made 52 to 472 false objects.
  • Claude found 7 to 10 of 28 test tanks, and made 14 to 34 false objects.
  • One Astra reply fails on false objects (472).
  • The Astra shape tests can explain its higher recall. This experiment does not prove that.
  • This does not show that one model is better. The sample is 3 replies for each model, and the intervals overlap.
  • The Astra lead on Breakout in section 6 did not occur here. This is one task.

Isolation of the Codex path

Astra ran through the Codex CLI [32]. Codex differs from the Claude path in section 4:

  • The call runs from an empty folder, with an empty Codex home. That home holds only a link to the login.
  • The tool turns off every enabled tool feature, and removes user configuration and rules.
  • Codex still names some tools to the model, and no flag removes the names. A probe showed that exec and spawn_agent both fail.
  • A tool attempt shows only in the error log. The audit therefore reads the stream and the error log. It rejects a run with any attempt. There were no attempts.
  • Codex has its own base instructions. The Claude path uses one short system prompt.
  • The token counts of the two tools may not be comparable.
  • OpenAI received the fact sheet numbers, with the owner's approval. It received no pixels.

12.9 Zero-shot detector

RT-DETRv2-S from LibreYOLO [31] has DOTA [29] weights, with a storage-tank class. It had no training on this image, and it had no weight edits. It takes about 5 seconds on one card. The settings were fixed before the run, from earlier work on the 2015 image: scale 1.5, score >= 0.70. A second run at native pixels is for comparison only.

12.10 What the results show

The results support these statements:

  • An LLM can write a working image network from zeros and a short fact sheet, with no tools and no training. This occurred in 6 of 6 write replies, on one image.
  • The written networks beat zero networks, random networks and the fact rule.
  • A small edit can improve a failed network, on this image. Plain programs can make the same edit.
  • For this task, a ready-made detector or real training is the practical choice.

The results do not support these statements:

  • They do not show that an LLM can repair a network with skill. The test gave away the answer, and its control did not separate a reader from a copier.
  • They do not show that weight edits are better than training. No written network beats the network trained on the new image on val cells.
  • They do not show that one LLM is better than the other.
  • They do not show results for other images or other tasks.

12.14 Limits

  • The results come from one image pair. No other scene was tested.
  • The detector settings came from earlier work on 73 tanks in this same area. Thus its scores can be optimistic.
  • The score of 0.70 was not tuned on these cells. A lower score finds more tanks and can add false objects. That was not measured.
  • Filter LDA was corrected after final. The table uses the corrected fit, which used the test cells for its report only.
  • The torch and Segmentation Models PyTorch versions are recorded: 2.11.0 and 0.6.0. The versions of the other packages were not.
  • The replies' own claims about each path were not checked layer by layer.

13. Limits and next work

13.1 Known limits

  • Sample size is small: 1 read reply, 1 control reply, 1 Breakout reply and 3 Three Pads replies. Section 12.14 gives the limits of the tank experiment.
  • This project did not run Experiments 2, 3, 4, 6, 7 or 8 with an LLM. It only checks the saved Experiment 2 replies.
  • A person has not yet flown the game for this manual. The browser test operates the controls, but does not land by hand.
  • The game has no wind, no terrain and no rotation. These were left out to keep the state simple.
  • The page uses unseeded random numbers. Flights on the page do not repeat. Only the scorer uses seeds.
  • The Medium article was read in part only.
